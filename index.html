Bitcoin Architecture

The Missing Layer

Bitcoin's capabilities have grown one step at a time, each making the next possible. Markets, escrow and trading grew up off-chain because there was nowhere neutral for agreements to live. OODL fills that gap.

  1. Layer 1
    Settlement
    Irreversible value transfer secured by proof of work. The foundation everything else rests on.
    Bitcoin (BTC)
  2. Layer 2
    Payments
    High-frequency, low-latency transfers using pre-signed off-chain channels that settle to Layer 1.
    Lightning Network
  3. Layer 3
    Ownership
    Permanent digital artefacts. Bitcoin as a data layer hosting provable ownership records.
    Ordinals / Inscriptions
  4. Layer 4
    Coordination
    Signed agreements published on-chain and completed by any participant. Bitcoin as a neutral place for offers to live and be found.
    OODL · oodinals.com

A conceptual stack, not a protocol hierarchy. Every OODL transaction is an ordinary Layer 1 Bitcoin transaction.

Protocol Mechanics

Three-Transaction Lifecycle

Every OODL listing follows the same three-transaction pattern. No custodian holds funds at any stage, and Bitcoin validates settlement automatically.

  1. 01
    Commit Transaction

    Prepare

    The inscription is aligned to sat offset zero inside a Taproot carrier output, and the listing fee is paid up front.

    Inscription aligned to sat offset zero
    Taproot carrier output created
    Listing fee paid at commit time
  2. 02
    Reveal Transaction

    Publish

    The seller's signed offer PSBT is embedded in witness data. The offer is now public on Bitcoin. No sale happens yet.

    PSBT embedded in an oodl envelope
    Signed SIGHASH_SINGLE | ANYONECANPAY
    Indexers find it by the envelope tag
  3. 03
    Buy Transaction

    Execute

    Anyone extracts the PSBT, adds their inputs and outputs, signs and broadcasts. Bitcoin settles both sides at once.

    Buyer adds padding and payment inputs
    Wallet checks sat flow before signing
    Atomic on-chain settlement
Core Cryptography

The Signature Insight

OODL's trustless guarantee comes from one signature construction that has been in Bitcoin from the start. No new primitives. No smart contracts.

buy_transaction.psbt
// INPUTS
input_1: "buyer_padding"
input_2: "buyer_padding"
input_3: "seller_inscription"
input_4+: "buyer_payment"
 
// OUTPUTS
output_1: "padding_merge"
output_2: "inscription_receiver"
output_3: "seller_payout"
output_4+: "buyer_change"
 
// SIGNATURE
sighash: SINGLE | ANYONECANPAY (0x83)
commits_to: input_3 + output_3
open_to: any counterparty
 
// SAT FLOW
output_1: = input_1 + input_2
inscription: lands in output_2
SIGHASH_SINGLE

Seller commits to one input-output pair

The seller's signature binds their inscription input to their payout output. The price and destination are fixed. Changing them invalidates the signature.

ANYONECANPAY

Any counterparty can complete it

Unknown future participants can add their own inputs and outputs without breaking the seller's signature. The buyer doesn't need to exist when the offer is published.

Sat Flow

The inscription lands where it should

Small padding inputs come first and merge into output 1, so the inscription's sat starts output 2, the buyer's receiver. Wallets simulate this before signing.

Atomic Settlement

One transaction, both sides

The inscription transfer and the payment confirm in the same transaction, or neither happens. Partial execution is impossible.

For Developers

Build on OODL

The Oodinals-Nexus Loader is a single inscribed ES module. One import gives you wallet connection, inscribing, OODL listing and buying, and a listing indexer. No npm, no build step.

app.js
// Load the SDK from Bitcoin
const { default: Nexus } = await import(
  '/r/sat/534764996708771/at/-1/content'
);

await Nexus.connectWallet('unisat');
const state = Nexus.getWalletState();
const utxos = await Nexus.getSpendableUtxos(
  [state.paymentAddress]
);

// Fill a listing by inscription id
await Nexus.buyFromInscriptionId({
  inscriptionId: '<txid>i0',
  buyerPaymentUtxos: utxos,
  buyerChangeAddress: state.paymentAddress,
  buyerReceiveAddress: state.ordinalsAddress,
  feeRateSatPerVb: 10,
  broadcast: true
});

// Read listings
const mp = Nexus.createMarketplaceClient({ /* … */ });
const page = await mp.getListingsPage({ pageSize: 25 });
List, buy, index

The whole protocol in one import

sellWith3TxFlow publishes a listing, buyFromRevealTx and buyFromInscriptionId fill one, and createMarketplaceClient pages through listings.

Pin for production

Choose how updates reach you

Sat-latest imports (/at/-1/content) follow new versions automatically. For code that signs or moves assets, pin an exact inscription ID with /content/<id> so behaviour never changes underneath you.

Know the defaults

Fees and data sources

A 2,000-sat platform fee is included by default and can be changed or set to zero per call. UTXO, fee-rate and broadcast calls go through external APIs via a small popup proxy.

Ecosystem Roles

Who Participates

No single participant controls OODL or captures all its value. Every role is open to anyone.

📝

Intent Publishers

Sign an offer and publish it. No counterparty needed at listing time.

⚡

Executors

Find offers, add funding and complete the transaction. Anyone can do it.

💼

Wallets

Verify offers, check sat flow and sign. The interface most people use.

🔍

Indexers

Scan Bitcoin for listings and serve them to wallets. Compete on quality.

⛏️

Miners

Confirm settlement. Can also act as executors, at the same signed price as anyone.

Security Model

No Trusted Operator

OODL adds no new trust assumptions to settlement. Every guarantee below comes from existing Bitcoin consensus.

✅

Payout Commitment

SIGHASH_SINGLE locks the seller's payout output. No executor can redirect the payment without invalidating the signature.

✅

Pre-Execution Verification

Before signing, wallets check the seller's signature, confirm the input is unspent and simulate sat flow so the inscription lands in the buyer's output.

✅

Mutation Detection

Any change to the seller's signed input or output invalidates the signature, so tampered offers are rejected by the network.

✅

Unilateral Cancellation

To cancel, the seller spends the listed UTXO. Every copy of the offer, on-chain or shared privately, becomes invalid at once.

✅

Atomic Settlement

The inscription and the payment move in one transaction. Partial execution is impossible, so no arbitration is ever needed.

✅

No Consensus Changes

Every OODL transaction is valid under current Bitcoin rules. No soft fork, no miner signalling. Deployment needs tooling, not permission.

Known Limits

What OODL Can't Do Yet

Knowing the limits is part of the security model. Each follows from what today's signature flags can express: a seller can enforce the payment they receive, and nothing more.

✕

Asset-for-Asset Swaps

A seller can require bitcoin in return, but can't require a specific inscription or rune, because sat flow depends on inputs the seller doesn't sign.

✕

Trustless Bids

Buy orders and collection offers can't guarantee the buyer receives the asset. They need interactive signing or covenants.

✕

Royalties at Sale

Extra outputs like royalties can't be enforced when a listing is filled. OODL collects its fee at listing time instead.

✕

Automatic Expiry

nLockTime can delay when an offer becomes valid, but nothing can end it. A listing lasts until the seller spends the UTXO.

✕

Off-Chain Goods

Bitcoin can only enforce what it can see. Fiat payments, physical goods and delivered work are out of scope.

✕

Partial Fills

Each offer is all-or-nothing. Fungible assets are traded as fixed lots rather than divisible orders.

Covenant proposals such as OP_CTV and OP_CAT would lift several of these limits. OODL's intent format is versioned so new intent types can be added if they ever activate.
